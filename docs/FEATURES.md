## 5. Решения по неоднозначностям ТЗ

ТЗ просит задавать вопросы. До ответа ревьюера я принял такие решения — каждое меняется в одном месте:

| # | Вопрос | Решение | Где поменять |
|---|--------|---------|--------------|
| Q1 | В каком часовом поясе «сейчас» и «сегодня»? | В поясе офиса (`Asia/Almaty` по умолчанию, `NEXT_PUBLIC_OFFICE_TIME_ZONE`). Комната физическая, браузер и сервер (Vercel = UTC) должны совпадать | `shared/config/office.ts` |
| Q2 | Можно ли менять/удалять начавшуюся или прошедшую бронь? | Нет, только просмотр. Сервер отвечает `422 BOOKING_STARTED` | `hasStarted` в `rules.ts` |
| Q3 | Шаг выбора времени? | В UI 15 минут. API принимает любую минуту, правило шага не вводилось | `TIME_STEP_MINUTES` |
| Q4 | Код для «нарушены правила» (не конфликт)? | `422 VALIDATION_FAILED` + `violations[]`. Если правила нарушены и есть пересечение — 422, а не 409: 409 оставлен только для «мир изменился» | `classify` в `service.ts` |
| Q5 | Перенос брони на другую дату при редактировании? | Домен и API поддерживают, в форме дата фиксирована (дата брони) | `BookingForm` |
| Q6 | Максимальный горизонт бронирования? | Не ограничен | — |

## 6. Бэклог

| # | Идея | Почему не сейчас |
|---|------|------------------|
| B1 | 💡 Персистентное хранилище (Upstash/Postgres) вместо in-memory | На serverless у каждого инстанса своя память. Нужна только новая реализация `BookingRepository` |
| B2 | 💡 Оптимистичное создание/удаление | Для честной демонстрации 409 лучше ждать ответа сервера |
| B3 | 💡 e2e (Playwright): создать → 409 → другой слот | Сценарий покрыт компонентным тестом |
| B4 | 💡 Перетаскивание/растягивание брони на таймлайне | Вне таймбокса; клавиатурная альтернатива уже есть (форма) |
| B5 | 💡 i18n (next-intl, как в daily-mail) | ТЗ на русском; все строки UI в двух модулях — переезд механический |
| B6 | 💡 Prefetch расписания на сервере (HydrationBoundary) | Тогда пропал бы видимый loading-state, который ТЗ просит показать |
